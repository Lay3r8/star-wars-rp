# Slice 3 Product Specification — Roll, Review and Adjudicate

**Status:** PROPOSED — CROSS-DOMAIN REVIEW REQUIRED  
**Owner:** Product Lead  
**Selection source:** `docs/planning/slice-3-candidates.md`  
**Selected by:** Human Project Owner  
**Implementation authorization:** NO  
**Current-slice impact:** NONE until this specification is reviewed and accepted

This document is an initial Product specification for cross-domain review.

It does **not** mark Slice 3 as ACCEPTED.

---

# 1. Purpose

Slice 3 should prove one bounded resolution-authority workflow:

```text
Create resolution
-> Roll
-> immutable mechanical result
-> GM review
-> Accept OR Override
-> Finalize
-> optional Correct after finalization
-> coherent current state + append-only history
```

The slice must establish a durable conceptual distinction between:

1. **RAW ROLL**
2. **MECHANICAL RESULT**
3. **FINAL ADJUDICATED OUTCOME**
4. **CORRECTION / SUPERSESSION**

The slice is intentionally narrow.

It must not become a generic resolution engine.

---

# 2. Source-of-truth constraints

## FACT — accepted decisions

The specification must remain consistent with:

- D-001 — Custom D20 is first-party for MVP;
- D-002 — PostgreSQL is the source of truth for mutable campaign state;
- D-003 — strict `campaign_id` isolation;
- D-004 — GM retains final authority over interpretive and authoritative narrative/canonical changes; bounded deterministic effects may be mechanically derived and committed under an accepted policy;
- D-005 — Slice 1 accepted `Slice the terminal, reveal the secret`;
- D-006 — Slice 2 accepted Contact preparation/search/reveal.

## FACT — relevant implementation baseline

The current `ActionResolution` implementation is Slice-1-specific:

- mechanic is constrained to `slicing`;
- raw D20 is generated by the backend;
- modifier is resolved from the acting Character's slicing profile;
- total and binary mechanical outcome are persisted after Roll;
- success effect is pre-bound to one KnowledgeFragment and recipient Character;
- success consequence is applied later through explicit Apply;
- failure requires a concrete GM adjudication before Close;
- success and failure terminal states are currently separate;
- Player knowledge is not mutated by Roll itself;
- DomainEvent is append-only history, not the source of current state;
- Player projection is explicit and does not expose canonical GM models.

## FACT — already identified Product direction

The Human Project Owner has already selected the direction that:

- the GM should explicitly control the final adjudicated outcome;
- raw mechanical evidence should not be rewritten;
- finalized adjudications should be correctable/supersedable;
- correction must not pretend cognitively irreversible information can be unseen.

# 3. Exact proposed scenario

## PRODUCT PROPOSAL

Reuse the existing Slice-1 slicing scenario.

Do **not** introduce a second mechanic.

Scenario:

> Kara Venn attempts to slice an Imperial cargo terminal to discover where a confiscated shipment was transferred.

Existing bounded setup remains:

- one campaign;
- one GM;
- one Player;
- one assigned Player Character: Kara Venn;
- one Location: Imperial Cargo Terminal;
- one pre-authored KnowledgeFragment:
  - "The confiscated shipment was transferred to Dock 47.";
- one slicing modifier;
- one GM-selected DC;
- one declared Intent;
- one declared Risk;
- one pre-bound success effect:
  - Kara becomes `AWARE` of the KnowledgeFragment.

The risk may remain:

> "On failure, Imperial security notices the intrusion."

The existing failure flow may continue to require a concrete failure adjudication before finalization.

## WHY THIS SCENARIO

This scenario is preferred because it already proves:

- D20 resolution;
- pre-bound consequence;
- GM-only resolution commands;
- persistence;
- authorization;
- CharacterKnowledge disclosure;
- atomic Apply;
- failure adjudication;
- reload;
- history.

Slice 3 should isolate the **authority/finalization/correction** problem instead of adding unrelated mechanics.

# 4. Proposed conceptual contract

## 4.1 RAW ROLL

### PRODUCT PROPOSAL

Raw roll is:

- the backend-generated natural D20 value;
- created exactly once by Roll;
- immutable after Roll.

For this slice:

```text
raw_roll = natural d20 in [1..20]
```

The GM must not be able to edit, replace, reroll, or delete it through adjudication/correction operations.

A new roll requires a new resolution under fiction/rules that permit another check.

### CROSS-DOMAIN REVIEW REQUIRED

Game Design and Architecture must confirm:

- whether "immutable" is enforced purely through command/state rules or additionally through persistence constraints;
- whether any administrative repair path exists outside normal Product behavior.

---

## 4.2 MECHANICAL RESULT

### PRODUCT PROPOSAL

Mechanical result consists of:

- raw roll;
- resolved modifier;
- total;
- DC;
- mechanically derived binary result:
  - SUCCESS;
  - FAILURE.

For this slice:

```text
mechanical_total = raw_roll + resolved_modifier
mechanical_result = SUCCESS if mechanical_total >= DC else FAILURE
```

All five pieces become immutable after Roll:

- raw roll;
- resolved modifier;
- total;
- DC;
- mechanical result.

The GM cannot "override" by changing any of these values.

### PRODUCT INTENT

An override changes the **final adjudicated outcome**, not the mechanical evidence.

### CROSS-DOMAIN REVIEW REQUIRED

Game Design must confirm that this distinction is rules-valid.

Architecture must define the persistence boundary without silently generalizing the current resolution model.

---

## 4.3 FINAL ADJUDICATED OUTCOME

### PRODUCT PROPOSAL

The final adjudicated outcome is a separate GM-authoritative decision.

It is not populated merely because Roll occurred.

After Roll, the resolution is in a **reviewable, not-finalized** state.

The GM may choose:

1. **Accept**
   - final outcome = mechanical result;

or

2. **Override**
   - final outcome = opposite binary outcome for this slice.

For the current binary D20 scenario:

```text
Mechanical SUCCESS
-> Accept => Final SUCCESS
-> Override => Final FAILURE

Mechanical FAILURE
-> Accept => Final FAILURE
-> Override => Final SUCCESS
```

No third/partial outcome is introduced.

### CONSEQUENCE BINDING

The final outcome determines which bounded consequence path is eligible at Finalize:

**Final SUCCESS**
- apply the already pre-bound KnowledgeFragment disclosure;
- CharacterKnowledge becomes AWARE;
- append meaningful history;
- close/finalize resolution.

**Final FAILURE**
- do not reveal the success KnowledgeFragment;
- require/persist concrete failure adjudication;
- append meaningful history;
- close/finalize resolution.

### CROSS-DOMAIN REVIEW REQUIRED

Game Design must validate:

- whether the GM may override success to failure and failure to success;
- whether override changes "outcome" itself or only consequence interpretation;
- whether any fiction/rules constraint should limit override.

This Product spec proposes full binary override for the bounded scenario, but does not declare it ACCEPTED.

# 5. Common path

## PRODUCT PROPOSAL

The normal path must minimize live-play friction.

### Mechanical SUCCESS — common path

```text
Create resolution
-> Roll
-> show mechanical evidence
-> GM Accept / Finalize
-> success consequence commits
-> resolution finalized
```

The normal success path should not require:

- a free-text reason;
- a second confirmation after an explicit Finalize action;
- extra workflow screens.

### Mechanical FAILURE — common path

```text
Create resolution
-> Roll
-> show mechanical evidence
-> GM accepts FAILURE
-> provide/confirm concrete failure adjudication
-> Finalize
-> failure consequence/history commits
```

The concrete failure adjudication requirement already exists in Slice 1 and remains useful because the predeclared Risk is not always the exact final fictional consequence.

### PRODUCT QUESTION

UX should determine whether "Accept" and "Finalize" are:

- one action in the common path;
- or two distinct actions when a consequence preview materially helps.

Product preference: **one primary action when no additional decision is required**.

# 6. Override path

## 6.1 Availability

### PRODUCT PROPOSAL

Override is available only:

- after a valid Roll exists;
- before the current adjudication is finalized;
- to an authorized GM;
- for this one binary slicing resolution.

It is not available:

- before Roll;
- to a Player;
- to mutate raw/mechanical data;
- as a generic arbitrary consequence editor.

---

## 6.2 What Override may change

### PRODUCT PROPOSAL

Override may change only:

- proposed/final adjudicated binary outcome:
  - SUCCESS -> FAILURE;
  - FAILURE -> SUCCESS.

If final outcome becomes FAILURE:
- a concrete failure adjudication is required before Finalize.

If final outcome becomes SUCCESS:
- the existing pre-bound success effect becomes the consequence to commit.

---

## 6.3 What Override may not change

Override may not change:

- natural d20;
- modifier;
- total;
- DC;
- mechanical SUCCESS/FAILURE;
- acting Character;
- Location;
- pre-bound success recipient;
- pre-bound KnowledgeFragment;
- campaign;
- historical events;
- Player assignment.

Changing those requires a different operation or a new resolution and is outside this slice.

---

## 6.4 Override reason

### PRODUCT PROPOSAL FOR REVIEW

An override reason is **optional** for Slice 3.

Rationale:

- override is exceptional;
- audit may benefit from a short explanation;
- forcing text entry risks live-play friction and low-value boilerplate.

If provided, it should be persisted/history-visible to the GM.

### CROSS-DOMAIN REVIEW REQUIRED

Game Design:
- is a reason mechanically/narratively required?

UX:
- should an optional reason be inline, secondary, or omitted entirely?

Architecture:
- if stored, where should it live without creating a generic audit-comment system?

# 7. Finalize boundary

## PRODUCT PROPOSAL

Roll does not commit canonical success/failure consequences.

Canonical consequence commit occurs only at **Finalize**.

Finalize must be a single server-authoritative transactional operation for the selected final outcome.

### Final SUCCESS transaction conceptually

```text
authorize GM
-> lock/load resolution
-> verify raw/mechanical evidence exists
-> verify final adjudication = SUCCESS
-> validate pre-bound campaign references
-> create/maintain CharacterKnowledge = AWARE
-> persist finalized adjudication/current state
-> append meaningful DomainEvent/history
-> commit once
```

### Final FAILURE transaction conceptually

```text
authorize GM
-> lock/load resolution
-> verify raw/mechanical evidence exists
-> verify final adjudication = FAILURE
-> require concrete failure adjudication
-> persist finalized adjudication/current state
-> append meaningful DomainEvent/history
-> commit once
```

### PRODUCT REQUIREMENT

A failed transaction must not leave split state between:

- final adjudication;
- CharacterKnowledge;
- resolution current state;
- meaningful history.

# 8. Correction / supersession path

Correction applies only after Finalize.

## 8.1 Purpose

### PRODUCT PROPOSAL

Correction is not rewind.

It means:

> replace the current authoritative adjudication with a new one while preserving the prior adjudication and historical facts.

The GM selects **Correct outcome** on a finalized resolution.

The UI must show the immutable mechanical evidence and the currently finalized adjudication.

---

## 8.2 What may be corrected

### PRODUCT PROPOSAL

Within this slice, Correction may:

1. replace the current final outcome:
   - FAILURE -> SUCCESS;
   - SUCCESS -> FAILURE;

2. replace the concrete failure adjudication text when current corrected outcome is FAILURE;

3. attach a correction reason.

Correction may not modify raw/mechanical evidence.

---

## 8.3 Correction reason

### PRODUCT PROPOSAL

A short correction reason is **required**.

Rationale:

- correction changes already-finalized authoritative state;
- it is expected to be rare;
- preserving why a finalized decision changed materially improves audit coherence;
- unlike normal Accept, the added friction is limited to an exceptional path.

This remains open to UX/Game Design review.

---

## 8.4 Supersession semantics

### PRODUCT PROPOSAL

The newest finalized adjudication is the current authoritative resolution state.

The previous adjudication is not deleted.

History must preserve at minimum:

- prior final outcome;
- replacement final outcome;
- correction reason;
- correcting GM;
- timestamp;
- resolution identity.

The Product requirement is supersession semantics.

The exact relational/event representation belongs to Architecture.

No full event sourcing is implied.

---

# 9. Consequence correction matrix

The slice must explicitly test the difference between:

- technically compensable state;
- cognitively irreversible disclosure.

## 9.1 FAILURE -> SUCCESS correction

### PRODUCT PROPOSAL

If a resolution was finalized as FAILURE:

- no success KnowledgeFragment was revealed;
- a later correction to SUCCESS may safely apply the pre-bound success consequence at correction time.

Correction transaction:

```text
final FAILURE
-> GM Correct outcome to SUCCESS
-> preserve old failure adjudication in history
-> apply CharacterKnowledge = AWARE
-> update current final adjudication to SUCCESS
-> append correction/history event
-> commit once
```

This is an **additive, technically realizable correction**.

---

## 9.2 SUCCESS -> FAILURE correction

### PRODUCT PROPOSAL

If a resolution was finalized as SUCCESS:

- the Player may already have seen the disclosed claim;
- CharacterKnowledge may technically be deletable;
- deleting it would falsely imply the human Player can unlearn the information.

Therefore:

```text
final SUCCESS
-> claim disclosed
-> GM Correct outcome to FAILURE
-> current final adjudication becomes FAILURE
-> require concrete failure adjudication
-> preserve prior success + disclosure in history
-> DO NOT delete CharacterKnowledge in this slice
```

The resolution's current authoritative adjudication and the historical disclosure may therefore legitimately differ.

This is intentional.

The system must not claim that correction erased what occurred cognitively.

### PRODUCT PRINCIPLE

**Technical reversibility does not imply fictional/human reversibility.**

---

## 9.3 FAILURE adjudication text correction

### PRODUCT PROPOSAL

If final outcome remains FAILURE, the GM may correct the concrete failure adjudication text.

Example:

```text
Old: "Security raises a general alarm."
New: "Only the terminal's local security log records the intrusion."
```

Current state shows the corrected adjudication.

History preserves the previous value.

No generic text-versioning framework is required beyond this bounded resolution history.

---

# 10. Irreversible effects

## 10.1 Technically compensable DB state

Examples may include:

- current final adjudicated outcome;
- current failure adjudication text;
- flags/current resolution state;
- a success effect that has not yet been shown to a human.

Architecture must determine the exact data mutations.

## 10.2 Cognitively irreversible human effects

For Slice 3, the key example is:

- a secret/claim already displayed to the Player.

Once displayed, correction cannot make the Player genuinely unaware.

Therefore Slice 3 explicitly rejects:

- deleting history to simulate that disclosure never happened;
- deleting CharacterKnowledge solely to pretend the Player never saw it;
- rewriting raw roll/mechanical evidence;
- claiming generic rollback semantics.

## CROSS-DOMAIN QUESTION

Game Design must define the fictional meaning of a corrected SUCCESS -> FAILURE where the Player retains knowledge historically obtained under the previous adjudication.

Product proposal:

- correction changes current canonical adjudication;
- the Player retaining the disclosed information is a historical/cognitive fact, not proof that the corrected final outcome is SUCCESS.

---

# 11. Proposed Player visibility

This section is deliberately **PROPOSED FOR REVIEW**, not accepted.

## PRODUCT GOAL

If the GM can override a mechanical result, Player trust benefits from not silently rewriting what the dice did.

However, this slice should not become a full Player resolution-history product.

## PRODUCT PROPOSAL — minimum

After Finalize, the assigned Player may see a read-only summary of the latest relevant resolution containing:

- raw d20: **YES**;
- modifier: **YES**;
- total: **YES**;
- DC: **OPEN — Game Design/UX review**;
- mechanical result: **YES**;
- final adjudicated outcome: **YES**;
- existence of override when final != mechanical: **YES**;
- override reason: **NO by default / GM-only**;
- full correction history: **NO**;
- corrected marker: **YES** if current final adjudication superseded an earlier one;
- current corrected final outcome: **YES**;
- correction reason: **NO by default / GM-only**.

The Player must never receive:

- GM-only hidden consequence details not fictionally disclosed;
- `gm_veracity`;
- arbitrary canonical ActionResolution fields;
- another Character's resolution data.

## ALTERNATIVE UNDER REVIEW

If Game Design/UX determine that Player resolution visibility adds disproportionate scope, the acceptance path may remain GM-only and the Player may see only the resulting consequence.

That decision must be explicit, not accidental.

# 12. Proposed GM UX requirements

## PRODUCT REQUIREMENTS

The GM surface must visibly separate:

### Mechanical evidence

- natural d20;
- modifier;
- total;
- DC;
- mechanical SUCCESS/FAILURE.

### Final adjudication

- pending GM review;
- accepted mechanical result;
- or overridden final result.

### Current status

- not finalized;
- finalized;
- corrected.

The frontend must not expose backend state-machine constants as user-facing vocabulary.

## Common path

Primary action should be obvious and fast:

- `Accept & Finalize` when no additional input is needed.

## Exceptional override path

Secondary action:

- `Override`.

Only then show any additional controls needed for the opposite outcome.

## Correction path

After finalization:

- `Correct outcome`.

The correction flow must show:

- original immutable mechanical result;
- current final outcome;
- proposed replacement;
- required correction reason;
- explicit note when prior human-visible consequences cannot be erased.

# 13. Proposed state semantics

This is Product-level semantics, not a persistence schema.

Conceptually:

```text
READY
-> ROLLED / AWAITING_GM_ADJUDICATION
-> FINALIZED
-> optionally CORRECTED / superseded adjudication
```

The exact state names and data model belong to Architecture.

The Product requirement is:

- Roll and Finalize are distinct;
- correction does not mutate mechanical evidence;
- latest adjudication is current;
- previous adjudications remain auditable.

No generic transition framework is requested.

---

# 14. Authorization and security

## PRODUCT REQUIREMENTS

Backend must enforce:

- only authenticated campaign GM may create the resolution in this scenario;
- only GM may Roll;
- only GM may Accept/Override/Finalize;
- only GM may Correct;
- Player cannot mutate resolution/adjudication;
- all embedded references remain same-campaign;
- Player visibility uses explicit projection/read model if implemented;
- client/frontend cannot rewrite roll, modifier, total, DC or mechanical result.

Frontend controls are not authorization boundaries.

---

# 15. History requirements

## PRODUCT PROPOSAL

Meaningful history should distinguish at least:

1. initial finalization;
2. correction/supersession.

History should make it possible for the GM to reconstruct:

- what mechanical result occurred;
- what final outcome was first chosen;
- whether it differed from mechanical result;
- what consequence was committed;
- whether a correction later superseded it;
- what the replacement adjudication became.

### PRODUCT NON-GOAL

History does not need to reconstruct all current state through event replay.

PostgreSQL relational state remains authoritative.

# 16. Proposed end-to-end acceptance scenarios

The final reviewed spec should retain a small E2E set that proves the essential distinctions.

## E2E A — Accept mechanical SUCCESS

```text
preconditions from Slice 1
-> create slicing resolution
-> Roll produces SUCCESS
-> Player does not yet know claim
-> reload
-> raw/mechanical result unchanged
-> GM Accept & Finalize
-> CharacterKnowledge = AWARE
-> history records finalization
-> reload
-> final outcome remains SUCCESS
-> raw/mechanical result unchanged
```

## E2E B — Override mechanical FAILURE to final SUCCESS

```text
create slicing resolution
-> Roll produces mechanical FAILURE
-> GM selects Override to SUCCESS
-> raw/mechanical evidence remains FAILURE
-> Finalize
-> success KnowledgeFragment is disclosed
-> final outcome = SUCCESS
-> history records mechanical FAILURE + overridden final SUCCESS
-> reload preserves both
```

## E2E C — Override mechanical SUCCESS to final FAILURE

```text
create slicing resolution
-> Roll produces mechanical SUCCESS
-> GM selects Override to FAILURE
-> enters concrete failure adjudication
-> Finalize
-> KnowledgeFragment is NOT disclosed
-> final outcome = FAILURE
-> raw/mechanical evidence remains SUCCESS
-> history records override
```

## E2E D — Correct finalized FAILURE to SUCCESS

```text
resolution finalized FAILURE
-> no claim disclosed
-> GM Correct outcome to SUCCESS
-> enters correction reason
-> correction transaction applies CharacterKnowledge = AWARE
-> previous FAILURE adjudication remains in history
-> current final outcome = SUCCESS
-> reload preserves corrected state and immutable roll
```

## E2E E — Correct finalized SUCCESS to FAILURE after disclosure

```text
resolution finalized SUCCESS
-> Player sees claim
-> GM Correct outcome to FAILURE
-> enters failure adjudication + correction reason
-> current final outcome becomes FAILURE
-> original SUCCESS remains in history
-> CharacterKnowledge remains AWARE
-> system does not claim the Player "unlearned" the claim
-> reload preserves all of the above
```

At least one E2E should use two distinct authenticated principals if Player visibility/consequence is involved.

# 17. Acceptance criteria

All criteria below are **PROPOSED** until cross-domain review completes.

## Raw roll / mechanical result

1. Roll creates exactly one natural D20 result.
2. After Roll, raw d20 cannot be changed by Accept, Override, Finalize or Correct.
3. Modifier cannot be changed by those operations.
4. DC cannot be changed by those operations.
5. Total cannot be changed by those operations.
6. Mechanical result cannot be changed by those operations.
7. Reload preserves the same raw/mechanical evidence.

## Final adjudication

8. Roll alone does not commit the success/failure canonical consequence.
9. GM can Accept the mechanical result.
10. GM can select Override before Finalize, subject to the reviewed Game Design contract.
11. Final SUCCESS applies only the existing pre-bound success effect.
12. Final FAILURE does not apply the success effect and requires the accepted failure-adjudication contract.
13. Finalize is atomic with its bounded consequence and meaningful history.
14. Repeated Finalize requests are safe/idempotent.

## Override

15. Override cannot mutate mechanical evidence.
16. Mechanical FAILURE -> final SUCCESS is testable end-to-end.
17. Mechanical SUCCESS -> final FAILURE is testable end-to-end.
18. History preserves that final outcome differed from mechanical result.
19. Any override reason behavior follows the final reviewed contract.

## Correction / supersession

20. Only a finalized resolution can be corrected.
21. Correction never rewrites raw/mechanical evidence.
22. Prior final adjudication remains preserved in history.
23. Replacement adjudication becomes current authoritative state.
24. Correction reason follows the final reviewed contract.
25. Final FAILURE -> corrected SUCCESS may apply the pre-bound success consequence atomically.
26. Final SUCCESS -> corrected FAILURE does not delete already-disclosed CharacterKnowledge.
27. Failure adjudication text can be corrected/superseded without deleting prior history.
28. Reload preserves current adjudication and historical supersession.

## Authorization / isolation

29. Player cannot Roll.
30. Player cannot Accept/Override/Finalize.
31. Player cannot Correct.
32. Non-member/other-campaign actors cannot mutate/read unauthorized resolution data.
33. Cross-campaign embedded references remain rejected.
34. Authorization is backend-derived.

## History

35. Initial finalization produces meaningful history.
36. Correction produces meaningful append-only history.
37. Current state is read from current relational state, not reconstructed by event replay.

## Scope control

38. No generic undo API exists.
39. No generic workflow engine exists.
40. No generic resolution engine is required.
41. No generic consequence/effect engine is required.
42. No Rule Effect DSL is introduced.
43. No realtime infrastructure is introduced.
44. No Player-side rolling is introduced.

# 19. CROSS-DOMAIN DECISION — questions for Game Design

   - mechanical SUCCESS -> final FAILURE;

## Override semantics

6. Is a reason required mechanically?

8. Does accepting the mechanical result require any explicit fictional adjudication beyond existing success/failure consequence rules?

## Failure semantics

9. Should final FAILURE still require a concrete failure adjudication after the predeclared Risk?
10. Can the predeclared Risk itself serve as the final consequence when no refinement is needed?

## Correction

11. What does a corrected adjudication mean in the fiction?
12. Can correction replace SUCCESS with FAILURE and vice versa after finalization?
13. Does correction create a new authoritative interpretation while preserving the original historical fact?
14. Is a correction reason required from a Game Design perspective?

## Irreversible consequence

15. When a previously finalized SUCCESS disclosed knowledge and is corrected to FAILURE, is retaining CharacterKnowledge acceptable?
16. How should the fiction interpret knowledge retained from a superseded adjudication?
17. Should any additional corrective narrative consequence be required, or is that outside the slice?

## Deferrals

18. Can crits, degrees, opposed rolls, partial outcomes, collaborative checks and rerolls remain fully deferred?
